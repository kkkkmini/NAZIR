# NAZIR — NON-FUNCTIONAL REQUIREMENTS (용량·성능·과부하)

> 문서 버전: 0.1(초안) · 기준일: 2026-11-28 · 목적: "사람이 몰려도 **틀리지 않는다**"(정확성, `TEST_PLAN.md` §1.1 불변식)에 더해 "사람이 몰려도 **멈추지 않는다**"(용량·성능·과부하 동작)를 숫자로 정의한다.
> 관련 문서: `TEST_PLAN.md` §14(부하 시나리오 → 본 문서 §7로 확장), `ARCHITECTURE.md` §5.2a·§7·§9, `DECISIONS.md` E-007·Q-013·A-024·A-031

## 1. 왜 이 문서가 필요한가

기능 테스트는 "혼자, 좌석 1~2개, Mock 결제가 즉시 응답"하는 조건에서 통과한다. 실제 오픈 순간은 다음 축이 **동시에** 커진다. 이 축들의 한계를 정하지 않으면 개별 기능이 모두 맞아도 합쳐 놓은 서비스가 멈출 수 있다.

| 축 | 개발 중 | 실제 오픈 | 막히는 지점(가설) |
|---|---|---|---|
| 동시 인원 | 1명 | 100명이 수십 초 안에 | 서버리스 인스턴스 증가 → DB 커넥션 한도 |
| 같은 자원 경합 | 없음 | 앞줄 좌석에 집중 | 같은 좌석 행 잠금 대기 → 연쇄 지연 |
| 외부 응답 시간 | Mock 즉시 | 토스 confirm 최대 60초(A-031) | 함수 실행 시간·커넥션 장기 점유 |
| 반복 행동 | 1회 클릭 | 새로고침 연타·더블클릭·여러 탭 | 재시도 폭주로 요청 수가 몇 배가 됨 |
| 시간 경과 | 몇 분 | 판매 창 수 시간, 7분 만료·1분 작업 상시 동작 | 커넥션·메모리 누수, 백그라운드 작업 밀림 |

원칙: **모든 한계는 존재한다. 한계를 미리 측정하고, 한계를 넘었을 때 "멈추지 않고 안내하며 실패"하도록 설계한다.**

## 3. 사용자 행동 모델 (부하의 "모양")

동시 접속자는 접속만 해 있지 않는다. 부하 테스트는 아래 비율과 행동으로 가상 사용자(VU)를 구성한다 [권장 — 실운영 로그가 생기면 교정].

| 유형 | 비율 | 행동 | 생각 시간(think time) |
|---|---|---|---|
| U1 예매자 | 55% | bootstrap → 본인인증(BOOKING) → claim → 회차 → 좌석맵 → 좌석 1~4석 선택 → `POST /orders` → (409면 좌석맵 재조회 후 다른 좌석, 최대 5회) → 결제수단 → `POST /orders/{id}/payments` → 결제창 체류 → 복귀 → 결제 상태 조회 → 확인서 | 인증 20~40초, 좌석 고르기 5~20초, 결제창 20~120초 |
| U1 변형 | U1 중 | 10% 결제창에서 이탈(7분 만료로 회수), 5% 결제 실패 후 재시도, 5% 결제 전 취소 후 재예매(D-001) | 위와 같음 |
| U2 구경꾼 | 25% | 공연·회차·좌석맵 반복 조회, 인증하지 않음 | 3~10초 |
| U3 조급형 | 10% | U1과 같은 경로이나 409를 받으면 즉시 재시도, 주문 버튼 더블클릭(같은 Idempotency-Key 2회 + 다른 키 1회), 탭 2개에서 동시 진행, 결제 후 뒤로가기·새로고침 | 0~1초 |
| U4 조회자 | 8% | LOOKUP 인증 → 주문 목록 → 확인서 | 5~15초 |
| U5 관리자 | 1~2명 | 주문 목록·상세 조회, 좌석 차단/해제 | 10~30초 |
| 시스템 | 상시 | 백그라운드 작업 1분 주기(만료·재조회·READY 정리, ARCH §8), 결제 성공마다 Mock webhook 1~2회(중복 포함) | — |

**좌석 선택 분포:** 앞 3열(전체 좌석의 약 15%)에 선택의 60%가 몰리도록 가중치를 준다. 균등 분포로 테스트하면 경합이 거의 생기지 않아 결과가 낙관적으로 나온다.

**요청량 추정(100명 기준):**

|---|---|---|
| 좌석맵 조회(`GET /sessions/{id}/seats`) | 5초 주기 갱신 20 RPS + 수동 새로고침 | 50 RPS |
| 주문 생성(`POST /orders`) | 오픈 후 10초 안에 60건 + 409 재시도 2~3배 | 30 RPS, 같은 회차 |

## 4. 서비스 수준 목표 (SLO)

측정 구간: 회차 오픈 시각부터 매진 후 10분까지(판매 창). 서버 측 응답 시간 기준(외부 업체 대기 제외 항목은 따로 표시). 모두 [권장]이며 Step 6 첫 측정 후 조정한다.

| ID | 지표 | 기준 부하(100명) | 스파이크·3배 부하 |
|---|---|---|---|
| NFR-P1 | 좌석맵 조회 p95 / p99 | ≤ 300ms / ≤ 800ms | ≤ 800ms / ≤ 2s |
| NFR-P2 | 주문 생성 p95 / p99 (409 응답 포함) | ≤ 800ms / ≤ 2s | ≤ 2s / ≤ 4s |
| NFR-P3 | 결제 시작·상태 조회 p95 | ≤ 500ms | ≤ 1.5s |
| NFR-P4 | 결제 복귀 처리 중 **NAZIR 자체 시간**(Tx1·Tx2, PG 대기 제외) p95 | ≤ 1s | ≤ 2s |
| NFR-P5 | 페이지(SSR) 첫 응답 p95 | ≤ 1s | ≤ 2.5s |
| NFR-E1 | 5xx 비율 | < 0.5% | < 2% |
| NFR-E2 | 응답 없이 멈춘 요청(클라이언트 10초 timeout) | 0건 | 0건 |
| NFR-C1 | 불변식 INV-1~12 위반 | **0건** | **0건** |
| NFR-C2 | 판매 좌석 수 = 유효 티켓 수 ≤ 좌석 수, 1인 4석 초과 0건 | 항상 | 항상 |
| NFR-R1 | 다른 사람이 점유한 좌석이 내 좌석맵에 반영되는 시간 | ≤ 5초 | ≤ 10초 |
| NFR-R2 | DB 커넥션 사용률(최대 대비) | < 70% | < 90% |
| NFR-R3 | 부하가 사라진 뒤 정상 SLO로 회복 | — | ≤ 2분 |
| NFR-R4 | hold 만료 작업 지연(`hold_expires_at` 경과 후 회수까지) | ≤ 2분 | ≤ 3분 |

`409 SEAT_UNAVAILABLE`, `429`, 과부하 안내 `503`은 **정상적인 거절**이며 5xx 오류율(NFR-E1)에 넣지 않는다. 단 503 비율은 따로 기록하고, 기준 부하에서는 0이어야 한다.

## 5. 과부하 시 동작 — "예쁘게 실패하기"

| ID | 상황 | 서버 동작 [권장] | 사용자 화면 |
|---|---|---|---|
| NFR-O1 | DB 커넥션을 3초 안에 얻지 못함 | 즉시 `503` + `Retry-After: 2~5`(jitter), 트랜잭션 시작 안 함 | "접속자가 많습니다. 잠시 후 자동으로 다시 시도합니다" |
| NFR-O2 | 같은 좌석 행 잠금 대기 2초 초과(`lock_timeout`) | 트랜잭션 rollback, 좌석 경합으로 보고 `409 SEAT_UNAVAILABLE` 또는 `503`(재시도 가능) | 다른 좌석 선택 안내 |
| NFR-O3 | rate limit 초과(Q-013) | `429` + `Retry-After` | 대기 안내 |
| NFR-O4 | 토스 confirm 지연 | 기존 설계 유지: 60초 timeout·3분 보호·UNKNOWN(A-031). 대기 중 DB 커넥션·트랜잭션을 잡지 않음(ARCH §7) | "결제 확인 중" 화면, 자동 상태 조회 |
| NFR-O5 | 클라이언트 재시도 | 지수 백오프 + jitter(1→2→4초, 최대 3회). 주문 버튼은 응답 전 비활성화, 같은 시도는 같은 Idempotency-Key. 좌석맵 자동 갱신은 실패 시 주기를 늘림(5→10→20초) | 연타해도 요청이 늘지 않음 |
| NFR-O6 | 3배를 넘는 부하 | 대기열은 Phase 1 범위 밖 [권장]. NFR-O1·O3로 막고, 측정 결과 300명에서도 SLO를 못 지키면 대기열 도입을 재검토 | — |

`503` 응답 코드명(제안: `SERVICE_BUSY`)은 `API_SPEC.md` §2.1에 추가해야 한다(미반영).

## 6. 용량 설계 기준

### 6.1 DB 커넥션 예산 [외부 확인 E-007]

`앱 인스턴스 최대 수 × 인스턴스당 풀 크기 + 백그라운드 작업 + 관리 여유 ≤ DB max_connections × 0.7`

- 현재 `src/server/db/client.ts`는 `pg` 풀 기본값(인스턴스당 최대 10)을 쓴다. 서버리스에서 인스턴스가 10개만 떠도 100커넥션이 되어 소형 관리형 DB의 한도에 닿을 수 있다.
- [권장] 인스턴스당 풀 최대 2~5, 커넥션 획득 timeout 3초(NFR-O1), 호스팅이 서버리스면 트랜잭션 모드 풀러(PgBouncer 계열) 사용. 풀러와 interactive transaction·행 잠금 호환성은 ARCH §9의 확인 항목이며 NFR-RES-03으로 실측한다.
- 호스팅·DB 상품이 정해지면(E-007) 이 식에 실제 값을 넣어 고정한다.

### 6.2 DB 시간 제한 [권장]

| 설정 | 값 | 목적 |
|---|---|---|
| `lock_timeout`(예매·결제 트랜잭션) | 2초 | 인기 좌석 잠금 대기 줄이 끝없이 길어지는 것 방지(NFR-O2) |
| `statement_timeout` | 5초(관리자 조회 10초) | 느린 쿼리가 커넥션을 붙잡는 것 방지 |
| `idle_in_transaction_session_timeout` | 10초 | 트랜잭션을 연 채 멈춘 커넥션 회수 |
| interactive transaction timeout(Prisma) | 5초 | ARCH §7 "timeout 명시" 구체화 |

### 6.3 입력 크기 한계 (모든 입력에 상한을 둔다)

| 입력 | 상한 |
|---|---|
| 주문당 좌석 | 1~4석(D-006, 이미 DB 제약) |
| 요청 본문 | 공개 API 16KB, webhook 64KB [권장] |
| 좌석맵 응답 | 200석 기준 약 20~40KB 예상. 실측 후 압축 여부 결정 |
| 관리자 목록 | 페이지당 최대 100건, 페이지네이션 필수 |
| 백그라운드 작업 1회 처리량 | 배치당 최대 100행 + `SKIP LOCKED`(ARCH §8). 밀리면 다음 주기에 이어서 처리 |

### 6.4 rate limit과 공유 IP

한국 이동통신망은 여러 사용자가 같은 공인 IP를 공유하는 경우가 많다(통신사 NAT). 같은 회사·공연장 와이파이도 마찬가지다. **IP 단위 한도만으로 막으면 정상 관객 여러 명이 같이 차단된다.** IP 한도는 느슨하게(남용 차단용) 두고, 바인딩·인증 주체 단위 한도(Q-013)를 주 방어선으로 삼는다 [권장].

## 7. 테스트 시나리오

도구: **k6**(JavaScript 시나리오, 단계별 VU 조절) [권장]. 시나리오 코드는 `tests/perf/`에 둔다(미작성).

### 7.1 실행 환경 — 전용 `perf` 환경 필요 [미결정]

- **토스·NICE sandbox에 부하를 걸지 않는다.** 업체 rate limit·약관 위반 위험이 있고, 측정 대상은 NAZIR이다. 부하 테스트는 Mock provider로 하고, Mock에 실제와 비슷한 지연을 넣는다(ARCH §6.3 장애 주입).
- staging은 Mock 사용이 금지되어 있다(A-024). 따라서 **운영과 같은 호스팅·DB 등급 위에 `NAZIR_RUNTIME_ENV=test`(Mock, `_test` DB)로 배포한 별도 환경**이 필요하다. 로컬 측정은 경향 확인용이며, 서버리스 커넥션 문제는 실제 호스팅에서만 드러난다.
- Mock 지연 분포 [권장]: 토스 confirm p50 1초·p95 3초, 요청의 2%는 30~60초. NICE는 사용자 입력 시간(think time)으로 대체.
- 데이터: 실제 배치와 같은 200석 좌석맵 seed, 실행마다 초기화.

### 7.3 매 실행 후 사후 검사
