## 0. 표기

범위 표기는 **계획 범위**만 뜻한다. **구현 완료를 뜻하지 않는다.**

| 표기 | 의미 |
|---|---|
| **[P1]** | Phase 1 범위이며, v1.2 문서에 API 명세가 있거나 정적 페이지로 가능. 구현 여부와 무관 |
| **[P1·API 없음]** | Phase 1에 필요하지만 API 명세가 없음. **구현 가능 기능으로 보지 않는다.** 개발 확인 전까지 화면은 자리만 정의 |
| **[P1·확인 필요]** | 기존 API 명세의 조합으로 가능할 수 있으나 개발 확인 필요 |
| **[후속]** | Phase 2 이후 |
| **[미결정]** | 사용자 결정 대기 |

### 0.1 구현 상태 (2026-11-17)

| 구분 | 의미 | 현재 |
|---|---|---|
| API 명세 | v1.2 `API_SPEC.md`에 정의됨 | 아래 표에 페이지별로 표시 |
| API 구현 | 서버에 동작하는 API가 있음 | **없음.** `/api/v1/health`만 존재 |

## 1. 결정 사항 (2026-11-17)

| ID | 결정 | IA 반영 |
|---|---|---|

| D3 | 작품 전체 출연진만 표시. 회차별 캐스팅은 운영 방식 확정 전까지 미표시 | 공연 상세에 전체 출연진, 회차 화면에 출연진 없음 |

## 2. 영역과 구현 범위

| 영역 | 사용자 | 경로 | Phase 1 | 후속 |
|---|---|---|---|---|
| A. 관객 사이트 | 관객(비회원) | `/` | 공연 정보, 예매(인증·좌석·결제), 예매 확인·확인서, 정책 페이지 | QR 티켓, 자체 취소·환불 요청, 여러 공연 목록 |
| B. 운영 콘솔 | 기획팀(SUPER_ADMIN, STAFF) | `/admin` | 주문·결제·환불·좌석·확인 필요 사안·연동 실패 | 판매 상태 변경·결제수단·관리자 계정·감사 로그 화면은 API 확인 후 |
| C. 현장 입장 | 현장 스태프 | `/admin/entry` | **화면 없음.** 확인서와 별도 명단으로 수동 대조 | QR 스캔, 입장 처리, 중복 입장 방지, 현장 전용 권한 |

- 관객 사이트에는 콘솔 링크를 두지 않는다. `/admin`은 검색엔진 수집을 막는다.
- **STAFF ≠ 현장 스태프.** STAFF는 환불 기록·좌석 차단 권한을 가진 기획팀 역할이다. 현장 스태프에게 STAFF 계정을 주는 것을 전제로 설계하지 않는다. 현장 전용 권한은 후속 설계 사항이다.

### 3.1 홈과 공연 상세 통합 (U1)

| 시점 | `/` | `/shows` | `/shows/{slug}` |
|---|---|---|---|
| Phase 1 (〈나지르〉 단일) | 〈나지르〉 공연 소개·예매 랜딩(A1) | 없음 | 없음, 또는 `/`로 이동 |
| 여러 공연 판매 시 | 서비스 홈(대표 공연·공연 목록 안내) | 공연 목록 | 공연 상세(지금의 A1 구성을 그대로 사용) |

- 홈과 공연 상세를 지금 분리할 이유가 없다. 공연이 하나뿐이라 홈이 할 일은 "그 공연으로 안내"뿐이고, 두 페이지를 두면 같은 정보가 반복되고 예매까지 한 단계가 늘어난다.
- 확장을 위해 A1의 구성은 "공연 1개를 소개하는 페이지"로 만든다. 공연이 늘면 같은 구성을 `/shows/{slug}`로 옮기고 `/`만 새로 만든다.
- 예매 단계의 주소는 처음부터 공연 단위로 두는 것을 권장한다(예: `/shows/{slug}/booking/...`). 그러면 공연이 늘어도 예매 주소를 바꾸지 않아도 된다. 정확한 경로는 개발팀이 정한다.
- 기존 v0.1·v0.2 와이어프레임의 "공연 상세"는 A1에 해당한다. ID A2는 A1에 통합되어 쓰지 않는다.

## 4. 관객 사이트 (A)

### 4.1 페이지별 목적과 행동

API 구현·화면 구현은 모든 행이 **미착수**다(0.1). 아래 "API 명세"는 v1.2 문서에 명세가 있는지만 뜻한다.

| ID | 페이지 | 핵심 목적 | 주요 행동 | 범위 | API 명세 |
|---|---|---|---|---|---|
| A1 | 〈나지르〉 공연 소개·예매 랜딩 `/` | 작품을 이해하고 예매 시작 | 예매 시작, 회차 확인, 전체 출연진 확인, 정책 확인, 예매 확인으로 이동 | P1 | 있음 `GET /shows/{id}`, `/sessions`. 소개 콘텐츠·계산된 판매 상태는 없음(R-D, R-E) |
| A3-1 | 회차 선택 | 날짜·시간 결정 | 회차 선택, 랜딩으로 돌아가기 | P1 | 있음 `GET /shows/{id}/sessions` |
| A3-2 | 본인인증 | 좌석 선택 전 예매 자격 확보 | 인증 시작 → 외부 → 복귀 | P1 | 있음 `/identity-verifications` (BOOKING) |
| A3-3 | 좌석 선택 | 좌석 선택(동일 회차 최대 4석) | 좌석 선택·해제, 남은 가능 수 확인, 다음 | P1 | 있음 `/seats`, `/my-quota`, `POST /orders` |
| A3-4 | 주문 확인·결제수단 | 좌석·금액 확인 후 결제 | 결제수단 선택, 이메일 입력(선택), 결제, 취소하고 다시 고르기 | P1 | 있음 `/orders/{id}`, `/payment-methods`, `/cancel`, `/payments` |
| A3-5 | 결제 결과 | 결과를 정확히 알림 | 확인서 보기 / 결과 확인 대기 / 재시도 또는 처음부터 | P1 | 있음 `GET /orders/{id}/payments/{id}` |
| A4-1 | 조회 본인인증 | 내 예매에 접근 | 인증 시작 | P1 | 있음 `/identity-verifications` (LOOKUP) |
| A4-2 | 내 예매 목록 | 내 예매 찾기 | 상세 열기 | P1 | 있음 `GET /orders` |
| A4-3 | 예매 상세·확인서 | 입장에 필요한 정보 확인 | 확인서 보기, 결제 전 주문이면 결제 계속·취소, 결제 후 취소·환불은 문의 안내 | P1 (문의 채널 U4 미결정) | 있음 `/orders/{id}`, `/confirmation`, `/cancel` |
| A5 | 안내·정책 | 법정·심사 고지, 문의 방법 | 읽기 | P1 (내용 미정) | 해당 없음(정적) |
| A6 | 시스템 페이지 | 오류·만료 안내 | 다시 시도, 처음으로 | P1 | 해당 없음 |

- 본인인증(A3-2)은 **좌석 선택(A3-3) 전에 반드시 완료**한다(확정 D-004). 인증 없이 A3-3에 들어오면 A3-2로 보낸다.
- 회차 선택(A3-1) 뒤, 좌석 선택(A3-3) 앞에서 인증하는 IA 구조를 유지한다. 개발 문서와의 순서 차이는 8장 G4로 남긴다. 세션 시간 관련 예외는 11장에서 User Flow 검토 항목으로 넘긴다.
- 결제 후 취소·환불은 관객이 직접 처리할 수 없다(관객 API 없음, 수동 환불 D-007). A4-3에는 문의 안내만 둔다.
- QR은 Phase 1 확인서에 표시하지 않는다.

### 4.2 주문 상태별 관객 안내 (A3-5, A4-3 공통)

| 주문 상태 | 관객에게 보여줄 의미 | 다음 행동 |
|---|---|---|
| PENDING | 결제 전, 좌석 유지 중 | 결제 계속 / 취소 |
| PAYMENT_CONFIRMING · PAYMENT_UNKNOWN | 결제 결과 확인 중, 좌석 보호 중, 다시 결제 불가 | 기다리기, 나중에 예매 확인에서 보기 |
| REVIEW_REQUIRED | 운영팀 확인 중 | 문의 안내 |
| PAID | 예매 완료 | 확인서 보기 |
| EXPIRED · CANCELED | 예매가 성립하지 않음 | 처음부터 다시 예매 |
| UNFULFILLED | 결제는 되었으나 발권되지 않음, 환불 대상 | 문의 안내 |
| REFUNDED | 환불 완료 | — |

### 4.3 공통 영역

- **사이트 헤더:** 로고(`/`, 즉 〈나지르〉 랜딩), 예매 확인. 공연 목록 메뉴는 공연이 2개 이상이 될 때 추가.
- **사이트 푸터:** 이용약관, 개인정보처리방침, 취소·환불 규정, 고객 문의 안내, 사업자 정보.
- **예매 단계 헤더(A3 전용):** 현재 단계, 선택한 회차 요약, 좌석 점유 후 남은 시간(서버 기준), 예매 나가기.
- **인증 상태 표시:** 인증된 이름(마스킹), 인증 세션 남은 시간, 인증 종료.

## 5. 운영 콘솔 (B)

### 5.1 메뉴별 목적과 행동

API 구현·화면 구현은 모든 행이 **미착수**다(0.1). 범위의 "P1"은 API 명세가 있다는 뜻이다.

| 메뉴 | 핵심 목적 | 주요 행동 | 범위 | 권한 |
|---|---|---|---|---|
| B0 로그인 | 기획팀만 접근 | 로그인, 로그아웃 | P1 | — |
| B1 운영 현황 | 지금 처리할 일을 한눈에 | 미해결 확인 필요 사안·결과 확인 중 결제·검증 중 환불·연동 실패 개수와 이동 | P1·확인 필요 | STAFF+ |
| B2 공연·회차 | 판매 대상 확인과 판매 상태 관리 | 조회, 회차 판매 상태 변경(판매 중·중지·종료·취소) | P1·API 없음 | 변경 권한 미결정 |
| B3 좌석 현황 | 회차별 좌석 상태 파악, 판매 제외 | 차단·해제 | P1 | STAFF+ |
| B4 예매 | 고객 문의 대응, 주문 추적 | 주문번호 검색, 상세(항목·점유·결제·환불·티켓·이력), 환불 요청 시작 | P1 | STAFF+ |
| B5 결제 | 결제 상태 확인 | PG 재조회 | P1 | STAFF+ |

- 공연 등록과 기본 정보(작품 소개, 출연진, 이미지, 가격 등) 수정은 콘솔에 두지 않는다. 개발팀이 관리한다(U2).

### 5.2 공통 영역

- 상단: 현재 관리자·역할, 로그아웃, 세션 만료 안내(유휴 30분 권장).
- 좌측 메뉴: 위 메뉴 순서. 미해결 개수 표시는 B1과 같은 확인 필요 항목.
- 검색: 주문번호·티켓번호. 전화번호는 기본 마스킹.
- 모든 변경 처리는 사유 입력과 확인 단계를 거치고 감사 로그에 남는다.

**현장 명단 원칙과 후속 검토**
- 정본은 DB다. Google Sheets는 DB의 **비동기 미러**이며(ARCH §6.4, Q-014 읽기 전용 권장) 정본으로 쓰지 않는다. 명단을 Sheets에서 뽑더라도 판단 기준은 DB다.
- 후속 검토 항목:
  - 최신성: 미러는 지연될 수 있다. 공연 직전 예매·환불이 명단에 늦게 반영될 때의 처리.
  - 개인정보: 명단에 넣을 항목과 마스킹 수준(Q-016, Sheets에는 마스킹된 전화번호만 권장).
  - 제공 방식: Sheets 공유, 출력물, 콘솔 내보내기 중 무엇으로, 누구에게, 언제까지 제공할지.

## 11. User Flow로 넘기는 검토 항목

현재 확정 정책(D-002 점유 7분, D-003 결제 확인 3분, D-004 좌석 선택 전 인증, D-015 예매 인증 세션 고정 30분·주문 생성 시 잔여 10분 이상)은 바꾸지 않는다. 아래는 정책 안에서 화면이 처리해야 할 예외다.

| # | 상황 | 검토할 것 |
|---|---|---|
| F-1 | 인증 후 좌석을 고르는 데 20분 넘게 걸려, 주문 생성 시점에 세션 잔여가 10분 미만 | 좌석 선택 중 남은 시간 안내 시점, 주문 생성이 거부될 때의 재인증 안내 |
| F-2 | 결제 실패 후 다시 결제하거나, 결제 전 취소 후 재예매할 때 세션 잔여가 10분 미만 | 재인증 경로와 선택했던 회차 유지 여부 |
| F-3 | 인증 직후 다른 회차로 바꾸고 싶은 경우 | 인증을 유지한 채 회차 선택으로 돌아가는 경로 |
| F-4 | 진행 중 주문이 있는 상태에서 세션이 만료 | **검증 항목.** 재인증으로 기존 주문에 다시 접근할 수 있는지는 현재 정책만으로 확정할 수 없다. API §3.2의 "주체 귀속" 문구, 브라우저 바인딩, 주문 접근 세션, 점유 만료와 함께 개발팀과 확인 |
| F-5 | 같은 회차에 이미 진행 중인 예매가 있음(D-008) | 기존 주문 확인·취소 경로. 이어서 결제할 수 있는지는 F-4와 함께 검증 |
| F-6 | 세션 만료 전에 인증 시간을 늘리고 싶은 경우 | 연장 불가(D-015). 재인증 안내만 |
